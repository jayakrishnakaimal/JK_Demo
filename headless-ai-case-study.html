01 Executive Summary

As AI agents move from assistants to autonomous operators — managing network fleets, resolving incidents, and taking consequential actions without user prompts — a critical design gap emerged: IBM had no established UX pattern for how humans should trust, oversee, and control an AI that acts invisibly.

I led a team of 5 designers to define this problem space from first principles, identify the four failure modes that cause autonomous AI deployments to break trust, and deliver a fully interactive prototype that demonstrates what a trust-first headless AI product looks like in practice.

Bottom line for leadership: This work gives IBM a defensible, research-backed design position in the headless AI market — ahead of Salesforce, ServiceNow, and Microsoft Copilot Studio — and a prototype that is UXR-ready and engineering-handoff-ready today.

04 The Problem

Headless AI agents — systems that monitor, decide, and act autonomously without a user initiating every step — are being deployed in network operations, IT service management, and enterprise automation. The interface disappears. But trust cannot.

#Failure modeBusiness consequence
01Silent authorityAgent takes high-stakes actions with no audit trail — compliance and accountability risk
02Alert fatigueOperators stop trusting escalations — critical events get missed
03Opaque reasoningApprovers always approve or always deny — human oversight becomes theatre
04Permission driftAgent scope expands beyond agreed governance — regulatory and reputational risk
Why this matters now: Every major enterprise AI platform is racing to deploy autonomous agents. The first platform to solve the trust and transparency layer wins operator adoption and enterprise procurement conversations. IBM has the design capability to lead — this work proves it.
05 The Design Framework

Each pillar directly addresses one or more failure modes, forming a complete trust architecture for headless AI products.

01 · Scope & Policy
3-segment permission toggles (Auto / Ask / Approval) per capability. Edit mode with change diff confirmation. Snapshot-based discard. Addresses silent authority and permission drift.
02 · Trace View
Structured reasoning trace per agent decision — confidence score, blast radius, historical case cross-reference, recommended action sequence, estimated recovery time. Addresses opaque reasoning.
03 · Contextual Chat
Natural language case interrogation — "What caused this?", "What happens if I deny?" — without leaving the decision context. Case-specific evidence, not generic answers. Addresses alert fatigue.
04 · Agent Identity
Persistent agent identity with composite trust score and 8-axis posture radar that morphs live as permissions change. Makes operating mode legible at a glance. Addresses all four failure modes.
06 The Prototype

Built to production fidelity — not a wireframe, not a Figma mockup. Every interaction, animation, and data flow is live and demonstrable to any stakeholder in a browser.

Canvas — Drag-and-drop operational dashboard
Anomaly cards dragged from Global Network Map expand into full analysis tiles with confidence scores, RCA charts, and Approve / Escalate actions. Live stat values tick with sparkle micro-interactions. Animated empty-state placeholder.
Agentic Trace — Case list with full reasoning
Searchable case list with multi-step reasoning gate visualisation, agent action ledger, confidence chart, and a contextual chat sidebar per case. Demonstrates the Trace View pillar end-to-end.
Policy Studio — Live permission editor with real-time posture
Edit mode with amber visual state, 3-segment toggles, save modal with human-readable diff, snapshot-based discard. Every toggle immediately updates 3 knob values and morphs the 8-axis radar — consequences visible before saving.
Configuration Testing — Digital twin simulation
5 pre-built scenarios simulated against a live network topology. Animated results, outcome badges, metric animations. Lets operators test policy changes against real scenarios before committing.
Slack integration — Functional outbound webhook
Real Slack Incoming Webhook — URL persisted to localStorage, per-anomaly send buttons, send-all batch, auto-alert on escalate. Block Kit payload with severity, service, and "View Dashboard" CTA. Demonstrates the escalation channel design pattern.
Technical credibility: Single HTML file, ~10,000 lines, no framework, no build step — live on GitHub Pages. This lets design present working software to engineering, not a Figma link. It removes the "can this actually be built?" friction from every stakeholder conversation.

08 Outcomes & Learnings
✓ Validated
The radar-permission coupling was the most discussed artefact in internal reviews. Making abstract permission changes visible as a polygon shift created consistent "aha" moments — stakeholders immediately understood consequence visualisation as a differentiator.
✓ Validated
The reasoning trace pattern — confidence, blast radius, cross-reference, recovery time — gave reviewers a credible mental model of agent justification. Multiple reviewers called it the most trustworthy AI interface they had seen in an IBM product.
→ Next iteration
Pillar labels need translation into operator language for user testing. "Scope & Policy" → "What can the agent do on its own" tested significantly better in informal reviews. The prototype already reflects this language.
→ New design question
The Slack integration revealed an open design space: when an agent alerts via a third-party channel, who owns the decision and what is the response UX? A dedicated "outbound escalation channel" pattern is now scoped for the next phase.
"The best interface is no interface — until the moment a human truly needs to be there. The design challenge is making that moment legible, trustworthy, and reversible."— Core design principle, Designing for Invisible UI
